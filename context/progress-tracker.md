## Architecture Decisions

- Tailwind v4 with `@theme inline` CSS variable mapping — no tailwind.config.js.
- shadcn/ui v4 with base-nova preset (Base UI + Lucide) — components live in `components/ui/` and must not be modified after generation.
- Dark-only — `:root` set to dark values, `<html class="dark">` activates shadcn dark: variants. No light/dark toggle.
- Ghost AI design tokens (`--bg-base`, `--text-primary`, `--accent-primary`, etc.) defined on `:root` and mapped to Tailwind utilities via `@theme inline` (e.g. `bg-base`, `text-copy-primary`, `text-brand`, `bg-accent-dim`).
- Next.js 16 renames `middleware.ts` to `proxy.ts` — Clerk's `clerkMiddleware` is still exported under that name from `@clerk/nextjs/server` but is consumed as the default export of `proxy.ts` at the project root.
- Clerk appearance uses `theme` (not `baseTheme`) in `@clerk/ui` v1.x; override Clerk's `variables` with project CSS custom properties so the auth UI tracks the rest of the design system with zero hardcoded colors.
- All `@liveblocks/*` packages must stay on a single aligned version (currently `^3.22.0`). `@liveblocks/node` (server) and `@liveblocks/react-flow` (client + `/node` server helper) both depend on `@liveblocks/core`; a version split loads two copies of core into one bundle, which breaks cross-copy `LiveObject` identity used by `mutateFlow`. Bump them together.
- AI design agent server → canvas writes go through `mutateFlow` from `@liveblocks/react-flow/node` (the server counterpart to the client's `useLiveblocksFlow`), not a bespoke storage schema — this keeps server-written nodes/edges identical to client-created ones.
- Shared AI activity state uses three Liveblocks-native channels, never a parallel realtime store: **broadcast room events** (typed `RoomEvent: AiStatusEvent`) for the high-frequency AI cursor, ephemeral and never persisted; **feeds** (`ai-status-feed`, one per room) for durable coarse status a mid-run joiner can still read; and **presence** (`thinking`) for whether an individual participant is waiting on a run. Feed payloads are validated (`parseAiStatusFeedMessage`) before display.
- The sidebar transcript has exactly one source: the `ai-chat` feed. Prompts, the AI's summaries, and AI failures are all published there (the AI's under a fixed `AI_CHAT_SENDER` with `role: "assistant"`), so every participant sees the same conversation and no client keeps a private message list to merge. Ephemeral run progress does not go there — it belongs to `ai-status-feed` and renders as the transient strip above the composer.
- Room chat lives on its own Liveblocks feed (`ai-chat`), never mixed into `ai-status-feed` — a machine progress line and a teammate's message must stay distinguishable, and the two have different lifetimes and readers. Liveblocks types feed payloads globally, so `FeedMessageData` is the union of both feeds' shapes (`AiStatusFeedMessage | AiChatFeedMessage`) and each reader narrows it by parsing.
- The Liveblocks `RoomProvider` wraps the whole editor workspace (`WorkspaceRoom`), not just the canvas, so the AI sidebar and the canvas share one room connection and one view of presence + status.
- AI request handlers never trust a client-supplied `projectId`: access is resolved from the authenticated user plus the `roomId`, and the id handed to the background task is the one read back from the database. `TaskRun` (runId → userId) is the record every run-scoped token is checked against, so realtime subscriptions can only read runs their owner started.
- Generated artifacts are addressed by a server-generated id, never by a client-supplied path: the spec id is minted in the task, the blob path is derived from it (`specs/{projectId}/{specId}.md`), and the resulting blob URL is stored in `ProjectSpec.filePath` and read back through `@vercel/blob`'s `get()`. Because the store is private, the URL is not a capability — every read goes through a route that re-checks project membership and the spec→project relation, so blob URLs are never returned to a client.

- New API routes trigger tasks by id with a **type-only** import (`tasks.trigger<typeof someTask>("some-task", payload)`), per the pinned `@trigger.dev/sdk` authoring skill — importing the task instance drags its AI/Liveblocks dependencies into the route bundle. `POST /api/ai/design` predates this and still imports `designAgent` directly.

- Generated Markdown is rendered to React elements from a parsed block tree (`lib/markdown.ts` → `components/editor/markdown-view.tsx`), never through `dangerouslySetInnerHTML`. Spec text is written by a language model and read by every collaborator on a project, so HTML in it must stay inert; link hrefs are additionally gated to `http(s):`/`mailto:`. This is why no Markdown-to-HTML library was adopted — the parser is scoped to the subset `trigger/generate-spec.ts` asks the model to produce, and grows only if the prompt does.

- A spec's content has exactly one client-reachable address: the download route. The preview reads it with `fetch(...).text()` rather than through a second "content" endpoint, so there is a single place where project membership and the spec→project relation are re-checked, and the list endpoint stays pure metadata.

- Collaborators are stored by email only (`ProjectCollaborator`) — no local user table. The owner is not stored as a collaborator row; "people with access" = owner (resolved from `project.ownerId` via Clerk `getUser`) + collaborator rows. Display names and avatars are resolved at read time from Clerk (`getUser` for the owner, `getUserList({ emailAddress })` for collaborators), with email/id-only fallback when no Clerk user exists or Clerk is unreachable.
